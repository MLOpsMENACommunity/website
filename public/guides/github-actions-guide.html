The Complete GitHub Actions Guide

GitHub Actions is a CI/CD and automation platform built right into GitHub — no external servers required. In plain words: you write a small instruction file (a "recipe"), and GitHub's computers follow that recipe automatically whenever something happens in your project — a push, a pull request, a new release, or even a fixed time of day. This guide assumes zero prior experience: every concept is explained from scratch, step by step, with copy-paste examples.

CI Continuous Integration CD Continuous Deployment Free unlimited minutes on public repos 20,000+ Marketplace actions

Introduction — What is GitHub Actions?

GitHub Actions is GitHub's built-in automation platform. Instead of installing and maintaining a separate automation server (like Jenkins or CircleCI), you simply add special instruction files to your repository — and GitHub runs them for you, on GitHub's own computers, whenever something happens: a push, a pull request, a new release, a comment, or even on a fixed daily schedule.

Think of it as a tireless robot assistant for your project: every time you save new code, the robot downloads it, checks it, tests it, packages it, and can even publish it — exactly the same way, every single time, without ever getting bored or making a typo.

New to CI/CD? A 60-second explanation

You will meet the terms CI and CD constantly in this guide:

  • Continuous Integration (CI) — every change you push is automatically built and tested. If something breaks, you find out within minutes instead of weeks, which keeps the main branch of your project healthy at all times.
  • Continuous Deployment / Delivery (CD) — once your changes pass all checks, they are automatically packaged and shipped: deployed to a server, published to npm or PyPI, built into a Docker image, and so on. No manual "build and upload" sessions.

GitHub Actions is simply one tool that provides CI/CD — with the big advantage that it lives exactly where your code already does.

Where do workflows live? Every workflow file must be placed in .github/workflows/ at the root of your repository, e.g. .github/workflows/ci.yml. Any file in that folder with a .yml/.yaml extension becomes an active workflow.

What you need before you start

  • A free GitHub account — genuinely all the tooling you need; the tutorial in the next section runs entirely in your browser.
  • Basic Git: how to make a commit and push it (editing files directly on github.com works too).
  • A repository — any language, any size. A brand-new empty repo is a perfect playground.
  • No credit card: public repositories run workflows for free, with unlimited minutes; private repositories get a free monthly allowance.

Your First Workflow — Hands-On Tutorial

Reading about automation is one thing — watching a machine run your instructions is another. This 5-minute tutorial takes you from zero to your first green ✓, using only your browser. You'll create a workflow, trigger it, and read its logs.

Step 0 — a one-minute YAML primer

Workflow files are written in YAML, a human-friendly text format. Four rules cover almost everything a beginner needs:

RuleLooks likeMeaning
Settings are key: value pairsname: CIA setting called "name" with the value "CI"
Indentation (2 spaces) shows nestingjobs:
  build:		"build" belongs to "jobs" — never use Tab, only spaces
Lines starting with - form a list- name: CheckoutOne item in a list (here: of steps)
# starts a comment# run testsIgnored by the machine — notes for humans

Step 1 — open (or create) a repository

Go to github.com/new and create a public repository — call it actions-playground. Public repos get unlimited free workflow minutes, so a playground repo costs nothing forever. (An existing repo works just as well.)

Step 2 — create the workflow file in the browser

  1. On your repository page, click Add file → Create new file.
  2. Type the full path .github/workflows/first.yml — as you type the slashes, GitHub automatically turns each part into a folder. The leading dot in .github is intentional.
  3. Paste the workflow below into the editor.
.github/workflows/first.yml — paste this
name: My First Workflow

on: push                    # the doorbell: run on every push

jobs:
  hello:                    # you choose this name
    runs-on: ubuntu-latest  # ask GitHub for a free Linux machine
    steps:
      - name: Say hello
        run: echo "Hello, GitHub Actions!"

      - name: Show run info
        run: |
          echo "Operating system : ${{ runner.os }}"
          echo "Repository       : ${{ github.repository }}"
          echo "Triggered by    : ${{ github.actor }}"

Step 3 — commit the file

Scroll down and click Commit new file. That's it — the workflow is now live, and committing it is itself a push event, so it triggers immediately.

Step 4 — watch it run

  1. Click the Actions tab at the top of your repository.
  2. You'll see "My First Workflow" in the left sidebar and one run in the list — "Initiated by your-username".
  3. Click the run, then click the hello job, then expand each step to see its output — including the exact lines your echo commands printed.
  4. A yellow dot means running, a green ✓ means success, a red ✗ means something failed.

What just happened?

  • Your commit fired the push event.
  • GitHub found .github/workflows/first.yml and read its on: trigger.
  • It started a brand-new Ubuntu virtual machine, created one job (hello), and ran the two steps in order.
  • The ${{ ... }} placeholders were filled in with real values (Linux, your-repo, your-username) before the commands ran.
  • The machine was destroyed afterwards. Every future push runs this recipe again, on a fresh machine — until you delete or disable the file.
Exercises (5 minutes each, highly recommended) ① Add a third step - run: date — commit and find its output. ② Change on: push to on: workflow_dispatch — now it runs only when you click "Run workflow" in the Actions tab. ③ Break it on purpose: add - run: exit 1, watch the red ✗, open the log, then fix it. Reading failure logs calmly is the #1 practical Actions skill.

Anatomy of a Workflow — The Big Picture

Everything in GitHub Actions is built from six building blocks. Understanding how they nest is 90% of learning the platform:

EVENTpush / PR / schedule
→
WORKFLOW.github/workflows/*.yml
→
JOBruns on a runner VM
→
STEPaction or shell command
→
RUNNERthe machine executing it

An event triggers a workflow. A workflow contains one or more jobs. Each job runs on a fresh runner (VM) and is made of steps. Each step is either a shell script or a pre-built action.

The six building blocks in plain English

TermWhat it really isAnalogy
EventSomething that happened in or around your repoThe doorbell ringing
WorkflowThe YAML file describing what to doThe full recipe
JobA group of steps running on one machineOne chapter of the recipe
StepA single command or actionA single instruction: "crack two eggs"
ActionA reusable step someone already wroteA pre-mixed spice blend
RunnerThe fresh virtual machine doing the workThe kitchen
.github/workflows/anatomy.yml — every keyword annotated
# ┌────────────────────────────────────────────────────────
# │ 1. WORKFLOW — the whole file is one workflow
# └────────────────────────────────────────────────────────
name: Learn GitHub Actions          # display name in the Actions tab

run-name: Deploy by @${{ github.actor }}   # dynamic run title (optional)

on: push                            # 2. EVENT — what triggers this

permissions:
  contents: read                    # least-privilege token (optional)

env:
  PROJECT: demo                     # workflow-wide env vars (optional)

defaults:
  run:
    shell: bash                     # default shell for `run` steps

jobs:                               # 3. JOBS — groups of steps
  build:                            # job id (you choose the name)
    name: Build & Test              # display name
    runs-on: ubuntu-latest          # 6. RUNNER — the VM to use
    timeout-minutes: 10             # kill job after 10 min (safety)

    steps:                          # 4. STEPS — sequential tasks
      - name: Checkout code         # step 1: uses an ACTION
        uses: actions/checkout@v4   # 5. ACTION — reusable unit

      - name: Setup Node
        uses: actions/setup-node@v4
        with:                       # inputs to the action
          node-version: '20'
          cache: npm

      - name: Install & test        # step 3: raw shell command
        run: |
          npm ci
          npm test

      - name: Share build output    # step 4: save ARTIFACT
        uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist/

How to read that file

  • Top to bottom: display name → trigger → global settings (permissions, env, defaults) → jobs:.
  • Under jobs:, build: is a job id you invent — its display name, runner, and steps are indented beneath it.
  • Under steps:, the dash lines run in order, on the same machine — files created by step 1 exist in step 2.
  • ${{ ... }} marks spots where GitHub injects real values at run time (here: the username who triggered the run).
  • Everything marked "optional" can be deleted — a minimal workflow needs only on:, one job, runs-on:, and steps:.
Pro tip Paste any workflow into the starter-workflows repo or use the "Actions" tab → "New workflow" in your repo to see dozens of ready-made templates for your language and platform.

01Workflows

A workflow is a configurable automated process defined in a YAML file — the complete "recipe" from the previous section. In practice: one YAML file = one workflow. A repository can contain as many as you like, each independent — e.g. ci.yml for tests, deploy.yml for releases, codeql.yml for security scanning. GitHub decides which one(s) to run by looking at each file's on: trigger.

Beginners usually start with a single ci.yml and split out more workflows as the project grows. Rule of thumb: group by purpose and trigger — tests run on every push, deploys only on the main branch, releases only on tags.

.github/workflows/ci.yml
name: CI                              # shown in the Actions tab
                                      # (optional — defaults to file name)

on:                                   # single event
  push

# ── multiple events ─────────────────────────────────────
# on: [push, pull_request, workflow_dispatch]

# ── event with filters (activity types / branch filters) ─
# on:
#   push:
#     branches: [main, 'release/**']  # only these branches
#     paths-ignore: ['docs/**']       # skip doc-only changes
#   pull_request:
#     types: [opened, synchronize, reopened]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "Workflow triggered by ${{ github.event_name }}"

    steps:
      - run: echo "Only the latest push deploys"

02Events (Triggers)

Events are the things that happen in or around your repository that can start a workflow — the on: block answers the question "when should this run?". GitHub offers 30+ events, and each can be filtered so you react only to what matters: only certain branches, only certain file paths, only certain tags, or only certain activity types (e.g. "PR opened" but not "PR closed").

The table below covers the events you'll meet in 95% of real projects. Don't memorize it — scan it now, come back when you need a specific behavior.

Most-used events reference

pushCommits pushed to a branch/tagCI on main, deploys
pull_requestPR opened/updated/closedTest PRs before merge
pull_request_targetLike above but runs in base repo context (secrets!)Label/comment on forks
workflow_dispatchManually from the Actions tab UIOn-demand runs with inputs
scheduleCron schedule (UTC)Nightly builds, cleanups

Example — every trigger style in one file

.github/workflows/triggers.yml
name: Trigger Examples

on:
  # ① push filtered by branch and path
  push:
    branches: [main, 'feat/**']        # glob supported
    paths:
      - 'src/**'
      - '!src/**/*.md'                 # exclude markdown

  # ② pull requests, filtered by activity type
  pull_request:
    branches: [main]
    types: [opened, synchronize, reopened]

  # ③ tags — publish when a version tag is pushed
  push:
    tags: ['v*.*.*']

  # ④ cron — "every day at 03:15 UTC" (min hour dom mon dow)
  schedule:
    - cron: '15 3 * * *'

  # ⑤ manual — button in the Actions tab, with input form
  workflow_dispatch:
    inputs:
      environment:
        description: 'Deploy target'
        type: choice
        options: [staging, production]
        default: staging
      dry_run:
        description: 'Skip the actual deploy?'
        type: boolean
        default: false

jobs:
  show:
    runs-on: ubuntu-latest
    steps:
      - run: |
          echo "event    = ${{ github.event_name }}"
          echo "ref      = ${{ github.ref }}"
          echo "target   = ${{ inputs.environment }}"
          echo "dry run? = ${{ inputs.dry_run }}"
Schedule gotchas Cron uses UTC. The shortest interval is 5 minutes, and scheduled runs are delayed during high-load periods (often 15+ min). Also, schedules are disabled after 60 days of repo inactivity.
Reading a cron expression The five fields of '15 3 * * *' are, left to right: minute (0–59), hour (0–23), day-of-month (1–31), month (1–12), day-of-week (0–6, Sunday=0) — so this one means "at 03:15 every day". A * simply means "every". Build expressions visually at crontab.guru, and remember to keep the whole expression quoted as a string.

03Jobs

A job is a set of steps executed on the same runner — one "chapter" of your recipe. Two beginner-critical facts:

  • Jobs run in parallel by default, each on its own separate machine. Add needs: to force an order ("deploy only after test passes"). If a needed job fails, dependent jobs are skipped — unless you opt out with conditions like if: always().
  • Every job gets a brand-new VM. Files created in one job are not visible in another — moving files between jobs is what artifacts (§11) are for.
.github/workflows/pipeline.yml — job dependency graph
name: Pipeline

on: push

jobs:
  lint:                                # ── runs first
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm run lint

  test:
    needs: lint                        # ── waits for lint
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false                 # don't cancel siblings on failure
    steps:
      - uses: actions/checkout@v4
      - run: npm test

  deploy:
    needs: [lint, test]                # ── waits for multiple jobs
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production            # may require approval (see §15)
    steps:
      - run: echo "deploying…"

  notify-on-failure:                   # ── runs even if deploy failed
    needs: deploy
    if: always() && needs.deploy.result == 'failure'
    runs-on: ubuntu-latest
    steps:
      - run: echo "🚨 deploy failed — sending alert"

Job-level keywords

KeywordWhat it does
runs-onRunner image / label: ubuntu-latest, windows-latest, macos-latest, or self-hosted label
needsJob(s) that must succeed first — creates the DAG

conditional jobs — the if expression in action
jobs:
  build:
    runs-on: ubuntu-latest
    if: |
      github.event_name == 'push' ||
      github.event.pull_request.draft == false
    steps:
      - run: echo "runs on real pushes and non-draft PRs"

  deploy-preview:
    runs-on: ubuntu-latest
    # expressions don't need ${{ }} inside if:
    if: github.event_name == 'pull_request'
    steps:
      - run: echo "PR preview deploy"

  deploy-prod:
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')
    steps:
      - run: echo "tag-triggered prod deploy"

04Steps

A step is an individual task: either a shell command (run) or a reusable action (uses). Steps in a job run sequentially in the same VM, so files created by one step are available to the next.

The two kinds of steps — run vs uses

run: — your own commanduses: — ready-made action
What it doesExecutes a shell command you writeRuns a reusable building block from the Marketplace
Examplerun: npm testuses: actions/checkout@v4
Give it options viaenv:with:
Use it forYour project's own commands (build, test, scripts)Common plumbing (check out code, install Node, upload files)
steps — run vs uses vs with
jobs:
  example:
    runs-on: ubuntu-latest
    steps:
      # ACTION step — checks out your repo into $GITHUB_WORKSPACE
      - name: Checkout
        uses: actions/checkout@v4
        with:
          fetch-depth: 0               # full history (default: 1 commit)

      # RUN step — plain shell, | for multi-line
      - name: Build
        run: |
          echo "Building on $(uname -a)"
          make build

      # per-step env + working-directory
      - name: Test
        run: npm test
        working-directory: ./backend
        env:
          NODE_ENV: test

      # keep going even if this step fails
      - name: Optional lint
        run: npm run lint
        continue-on-error: true

      # capture step OUTPUT for later steps
      - name: Get version
        id: ver
        run: echo "version=1.2.3" >> "$GITHUB_OUTPUT"

      # consume the output of a previous step
      - name: Use output
        run: echo "Version is ${{ steps.ver.outputs.version }}"

Step outputs vs job outputs

passing data between steps AND jobs
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:                           # ← expose for OTHER jobs
      version: ${{ steps.meta.outputs.version }}
    steps:
      - id: meta
        run: echo "version=$(cat VERSION)" >> "$GITHUB_OUTPUT"

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      # available as an env var here:
      - run: echo "Deploying v${{ needs.build.outputs.version }}"
        env:
          VERSION: ${{ needs.build.outputs.version }}
GITHUB_OUTPUT vs set-output The old ::set-output syntax is deprecated. Write key=value lines to the $GITHUB_OUTPUT file, then read them via ${{ steps.<id>.outputs.key }}. For multi-line values, use the delimiter form text<<EOF … EOF shown in the Cheat Sheet section.

05Actions

An action is a reusable unit of code — the building block you plug into a step with uses. Think of the GitHub Marketplace as an app store for automation: over 20,000 ready-made actions for checking out code, installing tools, logging in to cloud providers, posting comments, and almost anything else.

Every reference has the shape owner/repo@version. In actions/checkout@v4: actions is the organization that maintains it, checkout is the repository containing the action's code, and @v4 pins the major version. Actions can also come from your own repository (path reference) or run from a Docker image.

Referencing actions — three ways

action reference styles
steps:
  # ① PUBLIC repo — tag pinned (recommended: SHA-pinned)
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4

  # ② SHA pinning — most secure & reproducible (supply-chain best practice)
  - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

  # ③ Same-repo action — path to a directory containing action.yml
  - uses: ./.github/actions/my-custom-action

  # ④ Local checkout of another private repo action
  - uses: my-org/my-shared-actions/lint@main

    script: |
      await github.rest.issues.createComment({
        owner: context.repo.owner,
        repo: context.repo.repo,
        issue_number: context.issue.number,
        body: '✅ Build passed! Artifacts ready for review.'
      })

06Runners

A runner is the machine that executes your jobs — the "kitchen" where your recipe is cooked. GitHub provides ready-to-use virtual machines (Linux, Windows, macOS) with popular tools preinstalled; you just say which one you want with runs-on:. Alternatively, you can connect your own machines ("self-hosted runners") for special hardware or network needs.

Fresh machine every time — the #1 beginner surprise Each job runs on a brand-new VM that is destroyed when the job ends. Nothing persists between runs: no installed software, no downloaded dependencies, no leftover files. This is deliberate (clean, reproducible builds) — caching (§10) and artifacts (§11) exist to soften the cost.

Self-hosted runners

workflow targeting self-hosted runners by label
jobs:
  gpu-tests:
    runs-on: [self-hosted, linux, x64, gpu]   # ALL labels must match
    steps:
      - uses: actions/checkout@v4
      - run: ./run-gpu-benchmarks.sh

  windows-on-prem:
    runs-on: [self-hosted, Windows, X64]
    steps:
      - run: echo "Running on our own datacenter machine"
Self-hosted security Never use self-hosted runners on public repos with pull_request events — a forked PR could execute arbitrary code on your machine. Use GitHub-hosted runners for untrusted code.

Job containers — run the whole job inside Docker

container job — pinned language version everywhere
jobs:
  test-in-container:
    runs-on: ubuntu-latest
    container:
      image: node:20-bookworm           # everything runs inside this
      env:
        NODE_ENV: ci
      options: --cpus 2                 # docker create options
      volumes:
        - /data/cache:/cache
    steps:
      - uses: actions/checkout@v4       # checkout works inside too
      - run: node --version             # → v20.x

07Contexts & Expressions

Contexts are objects that expose data about the current run — think of them as ready-made variables GitHub fills in for you: who triggered the run, which branch, which commit, which OS. Expressions, written ${{ ... }}, are the syntax for reading that data and applying logic to it. For example, ${{ github.actor }} literally becomes alice in the final command if alice triggered the run.

${{ hashFiles('**/package-lock.json') }}            # stable cache key

Special status-check functions

always() / failure() / success() / cancelled()
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: exit 1
        id: failing

  cleanup:
    needs: build
    if: always()                      # run no matter what happened
    runs-on: ubuntu-latest
    steps:
      - run: ./teardown.sh

  report-failure:
    needs: build
    if: failure()                     # only when a needed job failed
    runs-on: ubuntu-latest
    steps:
      - run: curl -X POST $SLACK_WEBHOOK -d '{"text":"build broke"}'
Injection warning Never build shell commands directly from event data: run: echo "${{ github.event.pull_request.title }}" lets a malicious PR title execute arbitrary shell. Pass data through env vars instead:

env: TITLE: ${{ github.event.pull_request.title }} then run: echo "$TITLE"

08Environment Variables

Environment variables are named values that programs (and your shell commands) can read — like labeled fill-in-the-blanks. GitHub automatically provides many (GITHUB_REPOSITORY, GITHUB_SHA, …), and you can define your own at workflow, job, or step scope. When the same name is defined at several scopes, the innermost one wins.

scopes + defaults + dynamic env
env:                                  # ← workflow scope
  APP_NAME: my-app
  LOG_LEVEL: info

jobs:
  build:
    runs-on: ubuntu-latest
    env:                              # ← job scope (overrides above)
      LOG_LEVEL: debug
    steps:
      - name: Step scope
        env:                          # ← step scope (highest priority)
          TARGET: production
        run: echo "$APP_NAME / $LOG_LEVEL / $TARGET"

      - name: Dynamic — expression inside env
        env:
          BRANCH: ${GITHUB_REF##*/}   # shell param expansion works too
          SHA_SHORT: ${{ github.sha }}
        run: echo "branch=$BRANCH sha=${SHA_SHORT:0:7}"

      - name: Show GitHub defaults
        run: |
          echo "repo  = $GITHUB_REPOSITORY"       # owner/repo
          echo "ref   = $GITHUB_REF"              # refs/heads/main
          echo "sha   = $GITHUB_SHA"
          echo "ws    = $GITHUB_WORKSPACE"
          echo "token = $GITHUB_TOKEN"            # auto-injected
          echo "runner= $RUNNER_OS"               # Linux / Windows / macOS
env vs ${{ }} in run blocks Prefer $VAR_NAME shell syntax inside run: — it avoids YAML quoting issues and injection risks. Use ${{ }} for non-run fields (like if:, uses: with:, secrets).

09Secrets & Variables

Secrets are encrypted values (API keys, tokens, passwords). Variables are non-sensitive configuration. Both exist at organization, repository, and environment scope — the most specific wins.

Where to set them

ScopePath in GitHub UI
RepositorySettings → Secrets and variables → Actions
EnvironmentSettings → Environments → [env] → secrets
OrganizationOrg Settings → Secrets and variables → Actions

Adding your first secret — click by click

  1. Open your repository → Settings (you need admin rights).
  2. Left sidebar, "Security" section → Secrets and variables → Actions.
  3. Click New repository secret.
  4. Choose a name — uppercase with underscores, e.g. DEPLOY_KEY — paste the secret value, and click Add secret.
  5. Use it anywhere in your workflows as ${{ secrets.DEPLOY_KEY }}.

After saving, the value is encrypted and can never be displayed again — you can only update or delete it. That's fine: your workflows can still read it perfectly.

using secrets & vars
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production          # unlocks env-scoped secrets
    steps:
      - name: Deploy to cloud
        run: ./deploy.sh
        env:                         # secrets ALWAYS via env, masked in logs
          AWS_KEY:    ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          REGION:     ${{ vars.AWS_REGION }}        # non-secret config

      - name: Login to registry
        run: echo "${{ secrets.DOCKER_PW }}" | docker login -u user --password-stdin

      - name: Use the built-in token
        run: gh release create v1.0 dist/*
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}     # auto-created per run

The automatic GITHUB_TOKEN

GITHUB_TOKEN + permissions
# token is auto-injected in every job as GITHUB_TOKEN / github.token
# scope it down with top-level permissions:
permissions:
  contents: read          # read the repo
  pull-requests: write    # e.g. comment on PRs

jobs:
  label:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/labeler@v5
        with:
          repo-token: ${{ secrets.GITHUB_TOKEN }}
Secret rules Secrets are masked in logs, but anyone with repo admin access can read them via a workflow — treat secrets as visible to collaborators. They are also not passed to workflows triggered from forks (except via pull_request_target, which is exactly why that event is dangerous).

10Caching Dependencies

Because every job starts on a fresh machine (§06), dependencies get downloaded from scratch every single run — often the slowest part of a build. Caching fixes this: after one run saves the downloaded packages, later runs restore them in seconds. A 4-minute install can drop to a few seconds — and on private repos this directly saves billed minutes.

easy way — built-in cache in setup actions
- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: npm                        # caches ~/.npm automatically

- uses: actions/setup-python@v5
  with:
    python-version: '3.12'
    cache: pip                        # caches ~/.cache/pip

- uses: actions/setup-java@v4
  with:
    java-version: '21'
    distribution: temurin
    cache: gradle                     # caches ~/.gradle
generic way — actions/cache
- name: Cache node modules
  uses: actions/cache@v4
  with:
    path: |
      ~/.npm
      node_modules
    key: npm-${{ runner.os }}-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |                   # fallback prefix matching
      npm-${{ runner.os }}-
      npm-

# how the key works:
#   hit  = exact key match        → restored, cache-hit output = 'true'
#   miss = restore-keys prefix hit→ partial restore, then re-saved
#   miss = nothing matches        → empty, saved at job end
#
# hashFiles makes the key change whenever lockfiles change,
# so you get fresh deps after dependency updates automatically.
Cache limits 10 GB per repository — oldest unused caches are evicted. Caches are created with the branch scope: a PR can read caches from its branch and the default branch, but the default branch cannot read PR caches.

11Artifacts

Since each job runs on its own machine, files don't carry over between jobs by default. Artifacts are GitHub's built-in file-sharing system: one job uploads files (a build, a coverage report, binaries), another job downloads them, and you can grab them yourself from the run page in the UI. Unlike caches, artifacts are deliverables meant for people or later jobs, and they expire (default 90 days).

build → upload → download → deploy
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist-${{ github.sha }}     # artifact name
          path: |
            dist/
            coverage/
          retention-days: 7                 # override default 90
          if-no-files-found: error

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: dist-${{ github.sha }}
          path: download/
      - run: ls download/dist && ./deploy.sh download/dist
Cache vs Artifact Cache = machine-to-machine speedup (package managers), keyed & restored automatically, not browsable in UI. Artifact = deliverable output (binaries, coverage, logs), listed under the run's summary page and downloadable by humans.

12Matrix Builds

Does your library work on Linux, Windows and macOS? On Node 18, 20 and 22? A matrix runs the same job once per combination of values — you write the job once, GitHub multiplies it out. In the example below: 3 OSes × 3 Node versions = 9 combinations, minus 1 excluded = 8, plus 1 extra "include" job = 9 jobs in total, each shown as its own card on the run page.

cross-platform + multi-version matrix
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false                  # one failure ≠ cancel the rest
      max-parallel: 4                   # run at most 4 at once
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [18, 20, 22]
        exclude:                        # drop specific combos
          - os: macos-latest
            node: 18
        include:                        # add extra one-off configs
          - os: ubuntu-latest
            node: 20
            experimental: true
    name: Test (Node ${{ matrix.node }} on ${{ matrix.os }})
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test
        continue-on-error: ${{ matrix.experimental == true }}

Dynamic matrix — from a previous step's output

matrix expansion via fromJSON
jobs:
  discover:
    runs-on: ubuntu-latest
    outputs:
      packages: ${{ steps.set.outputs.packages }}
    steps:
      - uses: actions/checkout@v4
      - id: set
        run: |
          dirs=$(ls -d packages/*/ | jq -Rsc 'split("\n")[:-1]')
          echo "packages=$dirs" >> "$GITHUB_OUTPUT"

  build:
    needs: discover
    runs-on: ubuntu-latest
    strategy:
      matrix:
        package: ${{ fromJSON(needs.discover.outputs.packages) }}
    steps:
      - uses: actions/checkout@v4
      - run: npm build ${{ matrix.package }}

13Service Containers

Integration tests usually need a real database (or Redis, or RabbitMQ…) running somewhere. Service containers are extra Docker containers GitHub starts next to your job, already networked together — your steps simply connect to localhost on the mapped port, as if the database were installed on the same machine. The health-check options make the job wait until the service is actually ready before tests start.

Postgres + Redis services for integration tests
jobs:
  integration:
    runs-on: ubuntu-latest

    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: secret
          POSTGRES_DB: testdb
        ports:
          - 5432:5432                  # host:container
        options: >-
          --health-cmd "pg_isready -U app"
          --health-interval 5s
          --health-timeout 5s
          --health-retries 10          # wait until healthy before steps

      redis:
        image: redis:7
        ports:
          - 6379:6379
        options: --health-cmd "redis-cli ping" --health-interval 5s --health-retries 10

    steps:
      - uses: actions/checkout@v4
      - name: Run integration tests
        env:
          DATABASE_URL: postgres://app:secret@localhost:5432/testdb
          REDIS_URL: redis://localhost:6379
        run: |
          npm ci
          npm run test:integration
Linux only Service containers only work on Linux runners. For Windows/macOS, start services manually (e.g. brew services start postgresql) or run tests in a Linux container job.

14Reusable Workflows

Call one workflow from another — define your org's standard CI once and reuse it across hundreds of repos. The called workflow declares workflow_call with typed inputs and secrets.

.github/workflows/called.yml — the reusable template
on:
  workflow_call:
    inputs:
      node-version:
        required: true
        type: string
      run-lint:
        required: false
        type: boolean
        default: true
    secrets:
      deploy-token:                    # pass secrets explicitly
        required: false

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
      - run: npm ci
      - if: ${{ inputs.run-lint }}
        run: npm run lint
      - run: npm test
      - run: npm run deploy
        if: ${{ secrets.deploy-token != '' }}
        env:
          TOKEN: ${{ secrets.deploy-token }}
.github/workflows/main.yml — the caller
on: [push]

jobs:
  call-standard-ci:
    uses: my-org/shared-workflows/.github/workflows/node-ci.yml@v2
    with:
      node-version: '20'
      run-lint: true
    secrets:
      deploy-token: ${{ secrets.DEPLOY_TOKEN }}
    permissions:
      contents: read
Why reusable workflows? One source of truth for org-wide CI policy, updates ship to all repos by bumping a tag, and they don't count against your workflow quota like duplicated YAML does. Nesting is limited to 4 levels; max 20 unique reusable workflows per run tree.

15Environments & Approvals

An environment (Settings → Environments) is a deployment target (e.g. staging, production) with its own secrets and protection rules: required reviewers, branch restrictions, and wait timers.

Creating an environment — one-time setup

  1. Repository Settings → Environments → New environment.
  2. Name it (e.g. production) and confirm.
  3. Optionally add required reviewers — the listed people must approve before any job using this environment may proceed.
  4. Optionally restrict deployment branches (e.g. only main).
  5. Add environment-scoped secrets — production credentials that exist only here.

A job then opts in with a single line — environment: production — which activates all the rules above.

gated production deploy with manual approval
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:                # ← job PAUSES here until approvals pass
      name: production
      url: https://app.example.com     # shows a link on the run page

    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        run: ./scripts/deploy.sh
        env:
          DEPLOY_KEY: ${{ secrets.PROD_DEPLOY_KEY }}   # env-scoped secret

  rollback:
    runs-on: ubuntu-latest
    if: github.event_name == 'workflow_dispatch'
    environment: production
    steps:
      - run: ./scripts/rollback.sh

Protection rules you can enable per environment:

  • Required reviewers — job waits until an authorized user clicks "Review deployments" and approves (configurable timeout auto-denies).
  • Deployment branches — allow only main, protected branches, or a branch pattern like releases/**.
  • Wait timer — delay N minutes before the job starts (buffer for change windows).
  • Secrets scoped to the environment — production keys simply don't exist outside prod deploys.

16Docker in GitHub Actions

Build, scan, and push container images — either with raw docker build or the metadata/login/build-push trio that tags images the "right" way.

.github/workflows/docker.yml — build, tag, push
name: Docker Publish

on:
  push:
    branches: [main]
    tags: ['v*.*.*']

env:
  REGISTRY: ghcr.io
  IMAGE: ${{ github.repository }}      # owner/repo

jobs:
  build-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write                  # needed to push to ghcr

    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3      # BuildKit builder

      - uses: docker/login-action@v3             # auth to registry
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta                                  # smart tag + labels
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE }}
          tags: |
            type=ref,event=branch                 # main
            type=semver,pattern={{version}}       # v1.2.3 → 1.2.3
            type=semver,pattern={{major}}.{{minor}}
            type=sha,format=long                  # sha-abc1234…

      - uses: docker/build-push-action@v6
        with:
          context: .
          push: ${{ github.event_name != 'pull_request' }}
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha                    # reuse BuildKit layers
          cache-to: type=gha,mode=max
building a Dockerfile inside another folder
- uses: docker/build-push-action@v6
  with:
    context: ./backend
    file: ./backend/Dockerfile.prod
    build-args: |
      VERSION=${{ github.sha }}
    target: production          # multi-stage Dockerfile stage

  schedule:
    - cron: '0 6 * * 1'        # every Monday 06:00 UTC
  workflow_dispatch:

  contents: write
  pull-requests: write

    runs-on: ubuntu-latest

      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }

      - run: npm outdated || true
      - run: npm update
      - run: npm test

      - name: Open PR if changes
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"

Best Practices

🔒

Pin actions by SHA

uses: actions/checkout@<full-sha> # v4.2.2 — tags can be moved by maintainers; SHAs can't.

🕶️

Least-privilege tokens

Always set permissions: explicitly. Default GITHUB_TOKEN scope is read/write — narrow it to contents: read unless needed.

⏱️

Set timeouts

timeout-minutes prevents hung jobs burning your minute quota (default is 6 hours!).

🔁

Use concurrency

Group per-ref and cancel-in-progress: true so rapid pushes don't stack stale runs.

🏃

Fail fast & parallelize

Split lint/test/build into parallel jobs, then needs: them into a deploy stage.

📦

Cache everything expensive

Package managers, Docker layers (cache-from/to: type=gha), toolchains.

🧼

Quote shell env, not expressions

Pass untrusted event data through env: into "$VAR" — never inline into run:.

♻️

Reuse, don't copy

Composite actions & reusable workflows keep 100 repos' CI in sync from one place.

🚦

Gate production

Environments with required reviewers + deployment branch allow-lists for prod deploys.

Common Beginner Mistakes (and Fixes)

Every Actions user hits these. Recognizing them early turns hours of confusion into minutes.

#Symptom / mistakeWhy it happensFix
1Workflow rejected with a YAML syntax error (e.g. "mapping values are not allowed here")Tabs instead of spaces, or misaligned indentationUse 2 spaces per level, never Tab; indent children consistently under their parent
2Workflow never runs at allFile isn't in .github/workflows/, has a wrong extension (e.g. .yml.txt), or the on: trigger doesn't match what you didCheck the exact path and extension; test with on: push and commit something; look in the Actions tab
3Python 3.10 silently becomes 3.1YAML reads the unquoted number as a decimal float and drops the trailing zeroAlways quote versions: python-version: '3.10', node-version: '20'
4Second job can't find files the first job builtEach job runs on a separate fresh VM — filesystems are not sharedUpload an artifact in job 1, download it in job 2 (§11)
5npm: command not found or wrong tool versionTools must be set up in every job that needs them; preinstalled versions may differ from your project'sUse the setup actions (actions/setup-node, setup-python, …) in that job, right after checkout
6Secret shows as *** in logs and you think it's brokenThat's by design — GitHub masks secret values in all logsNothing to fix. To verify a secret exists, check its length instead: if [ -z "$KEY" ]; then echo "missing"; fi
7Workflow can't push code or create releases — 403 / Resource not accessibleThe automatic GITHUB_TOKEN is intentionally limitedDeclare what you need: permissions: with contents: write or pull-requests: write (§09)
8Scheduled workflow fires late — or stops firingCron runs in UTC, busy hours add 15+ min delays, and schedules pause after 60 days of repo inactivityConvert your local time to UTC; don't rely on to-the-minute timing; use workflow_dispatch as a manual backup
9Green locally, red ✗ on GitHub — no idea whyDifferent OS, different tool versions, missing environment, or case-sensitive pathsOpen the failing step's log and read from the first error upwards; enable debug logging (tip below)
10Workflow "changed behavior by itself" weeks laterUnpinned versions move: @v4, ubuntu-latest, and base images all update eventuallyPin actions by SHA for stability (§05) and consider pinned runner labels like ubuntu-24.04
11Cache "never hits"Exact-key match required; caches are branch-scoped (PRs can read the default branch's caches, not vice versa)Use hashFiles(...) in keys plus restore-keys: fallbacks (§10)
12Everything runs on every push, wasting minutesNo path filters and no concurrency groupingAdd paths-ignore: for docs, and concurrency: with cancel-in-progress: true to supersede stale runs
Debugging toolbox Re-run a failed run with "Enable debug logging" (Re-run jobs dropdown) for verbose logs, or add a repository secret ACTIONS_STEP_DEBUG = true. Print state while developing: echo "var=$VAR", ls -la, env | sort — and for stubborn cases you can even get an interactive SSH session in the runner via the tmate action.

Cheat Sheet

one-page reference
# ── MINIMAL WORKFLOW ─────────────────────────────────────
name: CI
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo hello

# ── TRIGGERS ────────────────────────────────────────────
on: [push, pull_request]                    # list
on: {push: {branches: [main]}}              # filtered
on: {schedule: [{cron: '0 3 * * *'}]}       # cron (UTC)
on: workflow_dispatch                       # manual button
on: workflow_call                            # reusable

# ── KEY EXPRESSIONS ─────────────────────────────────────
${{ github.sha }}            commit SHA
${{ github.ref }}            refs/heads/main
${{ github.ref_name }}       main
${{ github.event_name }}     push
${{ github.actor }}          who triggered
${{ github.repository }}     owner/repo
${{ github.event.* }}        webhook payload
${{ secrets.X }}             encrypted value
${{ vars.X }}                config value
${{ env.X }}                 env-var value
${{ matrix.X }}              matrix value
${{ steps.id.outputs.x }}    step output
${{ needs.job.outputs.x }}   job output
${{ inputs.x }}              dispatch/call input
${{ runner.os }}             Linux/Windows/macOS
${{ job.status }}            success/failure/…

# ── STEP OUTPUT PATTERN ─────────────────────────────────
- id: s
  run: echo "key=value" >> "$GITHUB_OUTPUT"
# read: ${{ steps.s.outputs.key }}

# ── MULTI-LINE OUTPUT ───────────────────────────────────
- id: m
  run: |
    {
      echo "text<<EOF"
      echo "line 1"
      echo "line 2"
      echo "EOF"
    } >> "$GITHUB_OUTPUT"

# ── DEFAULT SHELL VARS ──────────────────────────────────
$GITHUB_WORKSPACE   $GITHUB_SHA      $GITHUB_REF
$GITHUB_REPOSITORY  $GITHUB_TOKEN    $RUNNER_OS
$GITHUB_EVENT_NAME  $GITHUB_JOB      $GITHUB_RUN_ID

# ── COMMON COMBOS ───────────────────────────────────────
# checkout + lang + cache, in 3 steps:
- uses: actions/checkout@v4
- uses: actions/setup-node@v4
  with: {node-version: 20, cache: npm}
- run: npm ci && npm test

# debug logging when desperate:
#   Re-run with debugging → enable step debug logs
#   or set secrets: ACTIONS_STEP_DEBUG = true
